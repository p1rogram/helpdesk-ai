# Архитектура

> Пояснительные комментарии в коде помечены префиксом `AI:` — см. раздел «Про комментарии» в README.

## Принципы

1. **LLM не управляет диалогом.** `DialogEngine` — конечный автомат в коде. Модель вызывается ровно для двух
   вещей: понять сообщение (строгий JSON → `Analysis`) и сформулировать ответ — по одной статье базы
   знаний либо, если статьи нет, по фрагментам документации из RAG-индекса (стриминг). Решения
   «спросить / решить / эскалировать / закрыть» принимает код. Следствия: поведение тестируемо,
   дёшево (2 вызова на шаг максимум), и бота нельзя «уговорить» выйти из роли.
2. **Каталог — данные, не код.** Категории, уточняющие поля и статьи лежат в Postgres, редактируются
   через admin API, кэшируются в памяти по версии тенанта. Смена сферы = импорт JSON.
3. **Запрос→ответ синхронный, всё остальное — события.** Путь чата: HTTP + SSE (первый токен < 1 с).
   Побочные эффекты (уведомления, аналитика, интеграции с helpdesk) — события в Kafka.
4. **Никогда не падать.** Любая ошибка LLM → детерминированный fallback (классификация по BM25,
   шаги статьи дословно). Пользователь всегда получает ответ.

## Состояния обращения

```
intake ──(категория известна, confidence ≥ порога)──▶ clarifying* ──(обязательные поля собраны)──▶ solving
  │                                                                                            │
  └──(confidence < порога)──▶ choosing_category ──(кнопка)──▶ clarifying/solving               ├─ Помогло ──▶ closed (+ оценка)
                                                                                               ├─ Не помогло ──▶ вторая статья | offer_escalation
                                                                                               └─ Нужен специалист ──▶ offer_escalation

offer_escalation ──(«Да, создать»)──▶ escalated ──(оператор: «вернуть ИИ»)──▶ solving, escalationBlocked = true
```

Заявка специалисту создаётся только после явного согласия — состояние `offer_escalation`.
Пока обращение у оператора (`escalated`), помощник молчит: сообщения пользователя сохраняются и
уходят оператору. Оператор может вернуть обращение помощнику — тогда повторная передача по этому
обращению запрещена (`escalationBlocked`), помощник об этом знает и не предлагает её снова.

Уточнений — не больше `MAX_CLARIFICATIONS` (по умолчанию 2), и только по полям с `required: true`.
Значения, которые пользователь уже назвал, извлекаются дважды: моделью (свободная форма) и
детерминированными правилами из каталога (`extract`: регулярное выражение + белый список — номер
общежития, комната). Несуществующее значение отклоняется до поиска решения.

## Поток одного сообщения

1. `POST /api/tickets/:id/messages` (JWT → user, rate limit по user).
2. `inspectMessage()` — эвристики мата/агрессии/инъекций (0 мс, без LLM).
3. `LlmService.analyze()` — ответ модели валидируется `AnalysisSchema` (Zod); системный промпт
   стабилен по версии каталога → prompt cache. Ошибка/таймаут → `fallbackAnalyze()` по BM25.
4. Engine обновляет тикет (поля, тон, приоритет, summary), применяет правила `extract` и выбирает переход.
5. `KnowledgeService.search()` — BM25 по статьям категории (title×3, symptoms×2, steps×0.4).
6. Есть статья → `LlmService.solve()`: стрим markdown по статье + фрагменты RAG как справочник фактов.
   Нет статьи или модель вернула `[NO_SOLUTION]` → `RagService.search()` (BM25 + векторы, RRF) и
   `LlmService.answer()` строго по фрагментам с указанием источника; снова `[NO_SOLUTION]` →
   предложение специалиста.
7. `done` с сообщением, кнопками и карточкой; события в Kafka.

## Знания

Два слоя за одним движком:

| | Каталог | RAG-корпус |
|---|---|---|
| Хранение | `categories`, `kb_articles` (Postgres, admin API, seed из JSON) | `rag_chunks`: фрагмент + вектор (JSONB), хэш содержимого |
| Источник | ручная выверка: шаги, уточняющие поля, правила извлечения | краул help.tpu.ru и tpu.ru (`scripts/`), нарезка по заголовкам ~700 символов, чистка меню/футеров |
| Поиск | BM25 с префиксами | BM25 по фрагментам + косинус эмбеддингов `multilingual-e5-small` (ONNX в процессе API), слияние рангов RRF, порог для чисто векторных совпадений |
| Аудитория | `audience: public` для гостей | `public` — страницы сайта; `internal` — портал поддержки |

Эмбеддинги считаются локально — запросы пользователей не покидают сервер ради поиска. Ингест идемпотентен
(неизменённые фрагменты не пересчитываются) и запускается при старте или `POST /api/admin/rag/ingest`.
Переход на pgvector при росте корпуса — замена хранилища вектора за тем же `RagService.search()`.

## Kafka

| Топик | Продюсер | Консьюмеры | Ключ |
|---|---|---|---|
| `support.ticket.v1` | API | analytics (daily_stats), интеграции (Jira/ServiceDesk — точка расширения) | ticketId |
| `support.notification.v1` | API | notifier → Telegram Bot API | ticketId |
| `support.llm-usage.v1` | API | analytics (стоимость) | — |

KRaft-режим (без ZooKeeper), 6 партиций, retention 7 дней. Consumer groups → воркеры масштабируются
горизонтально; порядок событий по одному обращению гарантирован ключом. `EVENT_BUS=memory` даёт тот
же интерфейс `EventBus` in-process для разработки и тестов.

Почему не на пути запроса: очередь добавила бы латентность и потеряла бы стриминг; Kafka нужна там,
где есть несколько независимых потребителей и требуется буферизация/повтор.

## Безопасность

- Ключ Claude только на сервере (`LlmService`), не логируется, отдельный ключ с лимитом в консоли.
- Вход: Telegram `initData` проверяется HMAC-SHA256 (секрет из токена бота), constant-time compare,
  TTL 24 ч; выдаётся короткоживущий JWT. Гостевой вход только при `AUTH_DEV_BYPASS=true` (запрещён в prod).
- Rate limit на пользователя (JWT) / IP; лимит тела запроса 16 КБ; длина сообщения ≤ 2000.
- SQL: только Drizzle query builder (параметризация), никакой конкатенации.
- Prompt injection: пользовательский текст только в `user`-сообщении в конверте `<<< >>>`; инструкции
  оператора — в `system`; вывод модели валидируется Zod-схемой; у модели нет инструментов с побочными
  эффектами — эскалация делается кодом.
- XSS: markdown модели рендерится через DOMPurify с allow-list тегов; CSP на фронте и в Caddy.
- PII: тела запросов не логируются; храним platform user id, не телефон/почту.
- CORS allow-list; в проде фронт и API за одним origin (Caddy) — CORS не нужен.

## Производительность

- Один процесс Fastify, async I/O, пул соединений pg; каталог и индекс — в памяти по версии.
- Prompt caching: системные промпты — чистая функция от версии каталога (`cache_read_input_tokens`
  видно в логах при `LOG_LEVEL=debug`).
- `effort: low` + adaptive thinking для чата; `max_tokens` минимальны (1024/2048).
- Стриминг SSE с heartbeat, `flush_interval -1` в Caddy.
- Масштабирование: API stateless (JWT), N реплик за Caddy; worker — по партициям Kafka; Postgres —
  индексы по `(user_id, created_at)`, `(ticket_id, created_at)`.

## Точки расширения

- **VK / MAX**: `PlatformVerifier` (сервер) + `PlatformAdapter` (клиент) — по одному файлу на платформу;
  уведомления — ветка в `NotifierConsumer`.
- **Внешний helpdesk**: `HelpdeskConnector` — `NaumenHelpdesk` (help.tpu.ru) написан, включается ключом;
  другая система — ещё один класс за тем же интерфейсом.
- **Корпоративный вход**: `OidcProvider`, `LdapProvider`, `EmailCodeProvider` — включаются переменными.
- **Эмбеддинги / векторное хранилище**: интерфейс `Embedder` и `RagService` — pgvector или внешний API
  за той же сигнатурой.
- **Оператор**: консоль работает по SSE (`OperatorHub`), события — через шину, поэтому несколько
  реплик API видят одну очередь.
