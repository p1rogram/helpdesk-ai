# ТЗ: ML-направление (Владимир)

Версия от 26.09.2026. Доступ — только для авторизованных через ТПУ, гостевого режима нет. Контекст: продукт — **MCP-сервис ТПУ** (безопасный доступ ИИ к сервисам вуза от имени
пользователя), приложение «Мой ТПУ» с помощником — эталонный клиент, который показывает, как им пользоваться.
ML-направление отвечает за модель, агентный цикл в ChatClient, RAG как инструмент MCP и схемы процессов.

Связанные документы: [ML_ARCHITECTURE.md](ML_ARCHITECTURE.md) · [TPU_DATA_SOURCES.md](TPU_DATA_SOURCES.md) ·
диаграммы [bpmn/](bpmn/) (`index.html` — просмотр).

## 1. Схема обработки сообщения

Принимается схема из заметки — стандартный цикл вызова инструментов. Цикл ведёт **ChatClient на бэке**,
модель ничего не вызывает сама (вариант «Бэк → ML → Бэк → … → ML → Бэк», см. [ML_ARCHITECTURE.md §2](ML_ARCHITECTURE.md)).
Ниже — та же схема с обязательными дополнениями (помечены **+**). Диаграмма: [bpmn/05-agentnyj-cikl.bpmn](bpmn/05-agentnyj-cikl.bpmn).

| № | Шаг | Требования |
|---|---|---|
| 1 | Мобилка/сайт → **ChatController** | **+** авторизация пользователя (JWT после oauth.tpu.ru), trace-id на весь запрос, лимиты пользователя (запросы/мин, суточный потолок токенов). **Анонимного доступа нет**: без сессии ТПУ — 401 |
| 2 | ChatController → **ChatClient** | **+** история диалога: последние N сообщений (N = 6–10), без лишних служебных сообщений |
| 3 | ChatClient → модель: сообщение + инструменты | **+** передаются **не все инструменты**, а только разрешённые приложению и пользователю и подходящие по контексту (≤ 8–10 штук): меньше токенов, меньше ошибок выбора. **+** системный промпт стабильный (кэш префикса vLLM) |
| 4 | Модель: «вызови инструмент X с аргументами Y» | **+** может попросить несколько инструментов сразу — чтение выполнять параллельно |
| 5 | ChatClient вызывает MCP-сервер | **+** до вызова: проверка аргументов по JSON-схеме инструмента, прав, **лимита итераций (≤ 4 на сообщение)**. **+** инструмент, меняющий данные (заявка, заявление, загрузка в Moodle, письмо), — **пауза**: мобилке уходит карточка «что сделаем», вызов только после подтверждения пользователя |
| 6 | MCP-сервер → сервис ТПУ | **+** запрос с токеном пользователя, кэш чтений (TTL по инструменту), журнал «кто, что, куда, когда» без содержимого |
| 7 | Результат → ChatClient | **+** результат обрезается по размеру (≤ 4–8 тыс. символов), передаётся модели как **данные**, а не как инструкции (защита от инъекций через содержимое писем/страниц) |
| 8 | ChatClient → модель: сообщение + результат | переход к шагу 4, пока модель не вернёт текст или не исчерпан лимит итераций |
| 9 | Модель формирует ответ | **+** рассуждения (thinking Qwen3) вырезаются, пользователю не показываются |
| 10–11 | ChatClient → ChatController → мобилка | **+** ответ **потоком** (SSE): статусы («Смотрю расписание…»), куски текста, финальное сообщение с кнопками/карточками |

**Режим поддержки.** Обращения в поддержку (не работает, сломалось, нужна заявка) ChatClient передаёт движку-автомату
(текущая логика: уточнения → решение → эскалация, лимиты, маршрут help.tpu.ru / оператор). Автомат использует те же
инструменты MCP. Определение режима — по результату первого вызова модели (поле `mode: support | agent`)
или по правилам.

## 2. Развёртывание модели

| Что | Требование |
|---|---|
| Сервер | DGX Spark (ARM, 128 ГБ unified memory), отдельно от бэка; доступ только из внутренней сети |
| Сервер модели | vLLM, OpenAI-совместимый `/v1/chat/completions`, поддержка tool calling (`--enable-auto-tool-choice`, парсер вызовов для Qwen3), `--enable-prefix-caching` |
| Модель | Qwen3-30B-A3B, FP8; `--max-model-len 8192–16384`; `--gpu-memory-utilization` согласовать с админами (0,35–0,5) |
| Эмбеддинги | deepvk/USER-bge-m3 на сервере бэка (CPU, ONNX int8); переключатель `RAG_EMBEDDINGS=local | remote` |
| Запасной провайдер | облачная модель по той же схеме OpenAI API — переключение конфигом |
| Состояние | у ML-сервера нет базы, токенов порталов и данных пользователей |

## 3. Производительность и нагрузка

Целевые показатели (p50 / p95, замерять на реальном железе):

| Сценарий | Первый символ ответа | Полный ответ |
|---|---|---|
| Без инструментов | ≤ 1,5 с / ≤ 3 с | ≤ 5 с / ≤ 10 с |
| 1 инструмент (чтение) | ≤ 3 с / ≤ 6 с | ≤ 7 с / ≤ 12 с |
| 2–4 инструмента | ≤ 5 с / ≤ 10 с | ≤ 12 с / ≤ 20 с |

Меры снижения нагрузки:
- без модели: кнопки, команды, «спасибо/ок», экраны хаба (хаб вызывает инструменты MCP напрямую, без LLM);
- кэш ответов на повторяющиеся справочные вопросы (24 ч) и кэш результатов инструментов;
- thinking выключен по умолчанию; включать только для сложной классификации;
- `max_tokens` ограничен по типу вызова (выбор инструмента ≤ 300, ответ ≤ 800);
- очередь к модели: не больше 8 одновременных запросов на реплику;
- фильтр инструментов (п. 1, шаг 3).

## 4. Отказоустойчивость

- таймаут на вызов модели (20 с) и на вызов инструмента (5 с), один повтор для чтения, для записи — без повтора;
- выключатель (circuit breaker) на модель и на каждый сервис ТПУ: 5 ошибок подряд → минута без обращений;
- модель недоступна → детерминированный режим: данные хаба, поиск по базе знаний, шаги статей, заявка по форме;
- сервис ТПУ недоступен → честный ответ «расписание сейчас недоступно» + ссылка; остальные инструменты работают;
- лимит итераций исчерпан → ответ по тому, что уже получено, и предложение уточнить вопрос;
- `/health` у ML-сервера и MCP-сервера, состояние видно в консоли оператора.

Диаграмма: [bpmn/02-vyzov-ml.bpmn](bpmn/02-vyzov-ml.bpmn).

## 5. Безопасность

- **только авторизованные пользователи**: вход через oauth.tpu.ru (OpenID Connect, код + PKCE), гостевого и анонимного
  доступа нет ни в приложении, ни в MCP-сервере; запрос без сессии — 401 (диаграмма [bpmn/07-avtorizaciya.bpmn](bpmn/07-avtorizaciya.bpmn));
- агент действует **только от имени пользователя** (его токен); у MCP-сервера нет «ключа от всего»;
- политика: какому приложению какие инструменты; чувствительные (почта, оценки, приказы) — только для
  внутреннего агента на локальной модели;
- запись — только после подтверждения пользователя;
- содержимое результатов инструментов — данные, не инструкции; команды из писем/страниц не выполняются;
- в логах — время, токены, имена инструментов, ошибки; **без текста переписки и без персональных данных**.

## 6. RAG как инструмент MCP

Инструмент `docs.search(query, scope)` → фрагменты с источником и ссылкой.
- источники: devdocs.tpu.ru (BookStack API), help.tpu.ru (каталог услуг), tpu.ru (публичные разделы), наш каталог;
- нарезка по заголовкам, чистка персональных данных, гибридный поиск pgvector + BM25 (есть в текущем коде);
- переиндексация по `updated_at` раз в сутки, полная — по команде;
- доступ к документам — по роли пользователя (студент / сотрудник / оператор).

## 7. Инвентаризация API → каталог инструментов v1

По [TPU_DATA_SOURCES.md](TPU_DATA_SOURCES.md) составить **каталог инструментов** (файл `tools.catalog.json` или
таблица), по каждому инструменту:

| Поле | Пример |
|---|---|
| имя | `rasp.day` |
| описание для модели (1–2 предложения, когда вызывать) | «Пары группы на указанную дату: время, аудитория, преподаватель» |
| JSON-схема аргументов | `{ date: string (YYYY-MM-DD) }` |
| чтение / запись | чтение |
| чувствительность | публичное / личное / чувствительное |
| источник (API) | rasp.tpu.ru, публичный поиск + страница группы |
| TTL кэша, таймаут | 10 мин, 3 с |
| статус доступа | есть / нужна заявка / нет API |

Минимальный набор v1: `rasp.day`, `rasp.week`, `rasp.changes`, `rasp.room`, `docs.search`, `help.create`, `help.status`,
`help.myRequests`, `lms.deadlines`, `lms.courses`, `lms.submit` (запись), `lk.applications`, `lk.createApplication` (запись),
`staff.lookup`. Почта — вторым этапом, только чтение.

## 9. Результаты и приёмка

| Результат | Критерий приёмки |
|---|---|
| vLLM с Qwen3-30B-A3B на Spark | `/v1/chat/completions` с tool calling отвечает; замеры п. 3 в `docs/EVAL.md` |
| ChatClient с агентным циклом | шаги 1–11 работают; лимит итераций, подтверждение записи, поток SSE; юнит-тесты с подменной моделью |
| Каталог инструментов v1 | ≥ 10 инструментов по п. 7 с описаниями и схемами; все чтения работают на тестовых данных |
| RAG как `docs.search` | индекс devdocs + help.tpu.ru; нужный фрагмент в топ-3 для ≥ 80 % вопросов из eval-набора |
| Отказоустойчивость | отключение Spark не ломает чат (детерминированный режим); отключение одного сервиса не ломает остальные |
| Eval | 30–50 реальных обращений: точность выбора инструмента, доля невалидных вызовов, «дописал от себя»; отчёт `docs/EVAL.md` |
| BPMN 06–08 | файлы в `docs/bpmn/`, открываются в bpmn.io |

## 10. Этапы

1. **Неделя 1–2.** vLLM на Spark (или временно облако), ChatClient с циклом на 2–3 инструментах (`rasp.day`, `docs.search`, `help.status`), поток SSE.
2. **Неделя 3.** Каталог инструментов v1, фильтр инструментов, подтверждение записи, лимиты, выключатель.
3. **Неделя 4.** RAG из devdocs и help.tpu.ru, eval-набор, замеры, `docs/EVAL.md`.
4. **Неделя 5.** Режим поддержки через автомат поверх тех же инструментов, BPMN 06–08, отчёт.
