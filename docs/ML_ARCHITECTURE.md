# ML: архитектура взаимодействия бэка и модели

Ответы на вопросы из заметок ML-направления: отдельный сервер под модель, схема «кто кого вызывает»,
MCP, рассуждения модели, вложения (фото), нагрузка и отказоустойчивость. Диаграммы — в [bpmn/](bpmn/)
(`index.html` — просмотр в браузере, `.bpmn` — открыть и править в bpmn.io или Camunda Modeler).

## 1. Отдельный сервер под модель

ML-сервер (DGX Spark) — **сервис без состояния** с двумя адресами в стандарте OpenAI (vLLM отдаёт их сам):

| Адрес | Модель | Зачем |
|---|---|---|
| `/v1/chat/completions` | Qwen3-30B-A3B (FP8) | анализ сообщения (JSON), ответ по статье, выбор инструмента |
| `/v1/embeddings` | deepvk/USER-bge-m3 | векторы вопроса и фрагментов документации |

Два отдельных процесса vLLM: падение одного не останавливает другой. На ML-сервере нет ни базы, ни ключей
порталов, ни данных пользователей — его можно перезапускать и переносить, не трогая остальное.

## 2. Кто управляет процессом

Варианты из заметок:

1. Бэк → ML → Бэк → RAG → Бэк → ML → Бэк — **управляет бэк**;
2. Бэк → ML → RAG → ML → Бэк — **управляет ML**.

**Выбран первый.** RAG при этом — не отдельный сервис, а часть бэка: векторы лежат в той же Postgres (pgvector),
ML-сервер только считает эмбеддинги.

```
Бэк ──► ML: анализ сообщения → JSON                  ┐ параллельно
Бэк ──► ML: эмбеддинг вопроса                         ┘
Бэк:  поиск — кэш, каталог, pgvector + BM25 (~30 мс, без сети)
Бэк:  решение по правилам — уточнить / ответить / эскалировать
Бэк ──► ML: ответ по найденному (поток)
Бэк ──► пользователь
```

| | 1 · управляет бэк | 2 · управляет ML |
|---|---|---|
| ML упал | бэк отвечает по базе знаний (упрощённый режим) | не работает ничего |
| Доступ к БД и токенам пользователя | только у бэка | нужен и ML-серверу |
| Spark общий со студентами | ML без состояния | ML хранит логику и сессии |
| Кэш, лимиты, бюджет гостей | в одном месте | в двух |
| Смена модели / провайдера | одна переменная `.env` | переписывать оркестратор |

Задержку определяет генерация текста (анализ ~1 с, первое слово ответа ~0,5 с), а не сетевые переходы —
внутри вуза это доли миллисекунды. Схему выбираем по управляемости, а не по числу стрелок.

Диаграмма: [bpmn/01-obrabotka-soobshcheniya.bpmn](bpmn/01-obrabotka-soobshcheniya.bpmn).

## 3. MCP и «модель подумала — отправляем на бэк»

MCP (Model Context Protocol) — стандарт, по которому ИИ-клиент узнаёт о доступных инструментах и вызывает их.
**Внутри нашей схемы он не нужен**: «модель подумала» — это JSON `{"tool": "rasp.schedule", "args": {...}}`
в ответе модели. Бэк проверяет его по белому списку и схеме аргументов, сам вызывает портал с токеном
пользователя, пишет запись в журнал и отдаёт результат модели для пересказа. Модель не получает токенов и не
ходит в сеть. Действия, которые что-то меняют (заявка, заявление), — только после подтверждения пользователем.

Где MCP полезен — **наружу**: инструменты ТПУ (расписание, статус заявки, поиск по инструкциям) можно
опубликовать как MCP-сервер, и ими сможет пользоваться любой ИИ-клиент вуза (например, aichat.tpu.ru,
если это Open WebUI). Тогда проект — не отдельный чат, а слой инструментов для других систем.

Диаграмма: [bpmn/04-instrument-portala.bpmn](bpmn/04-instrument-portala.bpmn).

### Рассуждения модели

Режим рассуждений Qwen3 (thinking) включаем только там, где он повышает качество (сложная классификация);
для ответа по статье — выключен. Текст рассуждений пользователю не показываем: бэк вырезает его из ответа,
в статистику пишет только длину.

## 4. Вложения: фото проблемы для заявки в help.tpu.ru

Фото — это не вопрос MCP и не работа модели: файл проходит через бэк, модель байтов не видит.

1. Пользователь прикладывает фото в чате (кнопка в поле ввода; в Telegram — обычная отправка фото боту / из Mini App).
2. Бэк проверяет тип (jpg/png/heic) и размер (≤ 10 МБ), **удаляет EXIF** (там могут быть геометка и модель телефона),
   сохраняет во временное хранилище, привязывает к обращению. Модель получает только отметку «к обращению приложено фото».
3. При эскалации файл уходит вместе с заявкой: в Naumen — прикреплением к созданному запросу
   (REST-метод добавления файла к объекту), в консоль оператора — превью в карточке обращения.
4. Хранение: пока обращение открыто + 30 дней после закрытия, затем удаление. Для гостей вложения выключены.

Опционально позже: мультимодальная модель (например, семейства Qwen-VL) смотрит на фото и подсказывает категорию
(«на фото — розетка, похоже на кампус»). Это отдельная модель на Spark; к схеме добавляется ещё один адрес,
остальное не меняется. Если инструменты станут MCP-сервером, инструмент создания заявки принимает
не сам файл, а его идентификатор в хранилище.

Диаграмма: [bpmn/03-eskalaciya.bpmn](bpmn/03-eskalaciya.bpmn) (фото — в карточке подтверждения и в заявке).

## 5. Нагрузка, скорость, отказоустойчивость

**Меньше нагрузки на GPU**
- не звать модель для кнопок, команд, «спасибо/ок» — движок это уже умеет;
- кэш ответов на повторяющиеся вопросы (24 ч);
- анализ без thinking и с коротким `max_tokens`;
- не больше 8 одновременных вызовов, остальные — в очереди; vLLM сам объединяет запросы в батчи;
- лимиты гостей и суточный потолок токенов уже есть.

**Скорость**: анализ и эмбеддинг параллельно; ответ потоком; статусы «Определяю суть…».

**Отказоустойчивость** (диаграмма [bpmn/02-vyzov-ml.bpmn](bpmn/02-vyzov-ml.bpmn)):
- таймаут и один повтор на вызов;
- выключатель: после 5 ошибок подряд — минута без обращений к ML, ответы по базе знаний, сигнал в консоль;
- нет эмбеддингов → поиск только по словам (BM25); нет языковой модели → упрощённый режим; чат не падает;
- `/health` ML-сервиса видно в консоли оператора.

**Управляемость**: модель, адреса, лимиты — в `.env`; в логах время, токены, ошибки — без переписки;
оценочный прогон (eval) при каждой смене модели или промпта.
