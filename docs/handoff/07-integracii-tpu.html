Анализ · интеграции с порталами ТПУ · 18 сентября 2026

От бота техподдержки к единому окну студента

Что есть у ТПУ технически (обход 15 порталов, найденные API и точки входа), как это соединить с помощником, какие сценарии это открывает и как это обосновать перед ИТ-службой и менеджером.

Тезис в одном абзаце

У студента ТПУ — пятнадцать порталов: личный кабинет, расписание, Moodle, почта, облако, печать, техподдержка, заявления, библиотека, оплата, трафик, карта… У каждого свой вход, своя логика, свой поиск. Большая часть обращений в поддержку — не «сломалось», а «где это?», «как получить?», «что мне делать?». Помощник, который уже умеет понимать вопрос и вести диалог, становится ценным не тогда, когда отвечает по статье, а когда сам ходит в нужный портал: смотрит расписание группы, находит дедлайн в Moodle, создаёт заявление на справку, показывает статус заявки в help.tpu.ru — и всё это через один вход (единая авторизация ТПУ) и в одном чате. Это и есть схема с доски: пользователь → помощник → «хаб» с инструментами → порталы.

Ключевой факт: у ТПУ уже есть всё, что нужно для этого, — единая авторизация по стандарту OpenID Connect (oauth.tpu.ru), центральный REST API (api.tpu.ru, на котором работает сам личный кабинет), открытое API расписания и стандартные API у Moodle, Nextcloud, SOGo, BookStack, GitLab. Ничего не нужно «взламывать» или парсить — нужно попросить доступ и подключиться.

api.tpu.ru — кабинет разработчика (посмотрели изнутри)

Кабинет api.tpu.ru/dashboard открыт студенту по единой авторизации. Это самообслуживание, а не «написать письмо и ждать»:

  • Приложения → Добавить: полное и краткое название, описание, тип приложения, ссылка, уникальный ключ приложения и публичный ключ (SSL) — то есть запросы подписываются ключом приложения, а не паролем пользователя. Есть поля «платформы», «IP-адреса», «количество разработчиков» — можно завести команду.
  • Ключи доступа — отдельный раздел управления ключами.
  • Роли и правила доступа — 37 правил с алиасами (rasp.info.group «справка по группе», event.* мероприятия, object.request заявки, tpu.all / tpu.fakultet / tpu.kafedra — область данных, много exam.* — фонд оценочных средств). То есть у платформы уже есть модель разрешений: приложению выдают роли с набором правил, а не «всё или ничего».

Вывод для обоснования: ТПУ сознательно построил API как платформу для сторонних приложений с ролями и подписью запросов. Наш помощник — ровно такое приложение; регистрация — штатная процедура, а не исключение.

Зачем это вузу и менеджеру — обоснование

Меньше обращений в поддержку

Значительная доля заявок — «как/где». Если помощник сам показывает расписание, дедлайн, статус заявки или создаёт заявление, обращение не возникает. Это измеримо: доля диалогов, закрытых без заявки.

Один вход вместо пятнадцати

Единая авторизация ТПУ уже есть; помощник становится тем местом, где студенту не нужно помнить, в какой системе что лежит. Особенно для первокурсников — на доске это и было «Помочь первокурснику».

Персонализация без хранения данных

Помощник не копирует базы вуза: он спрашивает системы «на лету» от имени пользователя и ничего не сохраняет. Это проще согласовать по 152-ФЗ, чем любую витрину данных.

Проактивность

Не только отвечать, но и предупреждать: «завтра первая пара перенесена», «дедлайн через 2 дня», «по вашей заявке ответил специалист». Пуш в Telegram/VK/MAX уже есть.

Официальные API, а не парсинг

Всё, что мы нашли, — либо документированные API, либо стандарты (OIDC, iCal, CalDAV, WebDAV, Moodle WS). Решение устойчиво к редизайну порталов и не нарушает их правил.

Отличие от aichat.tpu.ru

Там — общая модель для разговоров. У нас — агент, который действует в системах вуза по правилам, с подтверждениями и журналом. Это не дубль, а следующая ступень.

Сценарии — что студент сможет сделать в одном чате

Как это выглядит в интерфейсе — отдельный макет: Единое окно · макет (телефон и десктоп, карточки порталов, подтверждения, вкладка «Сегодня», подключения, пуши).

Каждый сценарий — цепочка: понять намерение (уже умеем) → вызвать инструмент портала → ответить. Инструменты помечены так.

1. «Что у меня завтра?»— самый частый вопрос первокурсника.
  1. rasp.schedule(group, date) — пары, аудитории, преподаватели (группа известна из профиля oauth/api.tpu.ru).
  2. moodle.upcoming(days=1) — дедлайны и тесты.
  3. lk.events() — мероприятия из ЛК.
  4. Ответ одним списком с ссылками «открыть аудиторию на карте», «открыть задание».
2. «Нужна справка об обучении» / «Хочу сменить формат обучения»— «Получить справку» с доски.
  1. lk.services.tree() — найти нужное заявление в дереве МФЦ (сегодня там «Согласование ВКР», «Смена формата обучения»; у других ролей — больше).
  2. Уточнить недостающие поля тем же механизмом, что для заявок в поддержку.
  3. lk.services.create(...) — создать заявление от имени студента; вернуть номер и статус; следить за статусом и пушить изменения.
3. «Не могу зайти в Moodle / VPN / почту»— то, что уже умеем, но с доступом к системам.
  1. Диагностика по базе знаний (devdocs + наш каталог) — как сейчас.
  2. api.auth.info() — проверить, активна ли учётная запись, не истёк ли пароль (если API отдаёт).
  3. Не помогло — naumen.create(service="Доступ к ресурсам ТПУ", …) в правильную услугу от имени студента; статус — в чате.
4. «Что с моей заявкой?»
  1. naumen.myRequests() + lk.applications() — заявки в поддержку и заявления МФЦ одним списком.
  2. Комментарии специалиста — прямо в чат; «уточнить» → ответ уходит в заявку.
5. «Пропущу пару, кому написать?»
  1. rasp.schedule → преподаватель следующей пары.
  2. staff.lookup(ФИО) → кафедра, почта (телефонный справочник публичен).
  3. Черновик письма — открыть в почте по mailto: (без доступа к самой почте).
6. «Где корпус 10, ауд. 403Б?» / «Как добраться до общежития 12?»
  1. rasp.audience("403Б") — корпус и расписание аудитории; maps.link(корпус) — ссылка на карту кампуса.
7. «Сколько интернета осталось?», «Напечатай файл», «Оплатить общежитие»
  1. Первая очередь — глубокие ссылки в нужный раздел с уже выполненным входом (SSO). Вторая — API MyQ (печать из облака), netflow.
8. Проактивные уведомления (без вопроса)
  1. Раз в час: сравнить расписание группы с прошлой версией → «пара в 8:30 перенесена в к. 20, ауд. 406».
  2. Вечером: дедлайны Moodle на завтра, непрочитанные ответы по заявкам.
  3. Для первокурсников в сентябре: «завтра медосмотр 1 курса», «как получить пропуск» — из событий rasp.

Как это устроить в проекте

Схема с доски — центральный «хаб» с инструментами (там написано MCP). В терминах проекта это модуль integrations/ с одним интерфейсом на портал; движок диалога вызывает их как инструменты, решение — по-прежнему в коде.

Пользователь ──► Помощник (движок) ──► ToolHub ──► RaspTool      (Открытое API / iCal / поиск)
                      │                     ├──► LkTool        (api.tpu.ru: профиль, заявления МФЦ, события)
                      │                     ├──► MoodleTool    (веб-сервисы: дедлайны, оценки)
                      │                     ├──► NaumenTool    (help.tpu.ru: создать / статус / комментарии)
                      │                     ├──► DocsTool      (devdocs BookStack → RAG)
                      │                     └──► LinksTool     (maps, print, pay, netflow — глубокие ссылки)
                      ▼
               Модель: «понять» → какой инструмент и с какими аргументами (JSON), «объяснить» результат
  • Модель выбирает инструмент, код его вызывает. Как сейчас с категориями: JSON от модели вида {tool:"rasp.schedule", args:{date:"tomorrow"}} проходит валидацию (белый список инструментов, схема аргументов), и только тогда выполняется. Модель не получает токенов и не ходит в сеть сама.
  • Действия — только с подтверждением. Чтение (расписание, дедлайны) — сразу; запись (создать заявление, заявку) — показать, что будет отправлено, и кнопка «Отправить». Это уже принцип эскалации «по согласию».
  • Токены пользователя — на лету, не в базе. После входа через oauth.tpu.ru у нас есть access-token с коротким сроком; им подписываются запросы к api.tpu.ru. Для Moodle/Nextcloud — отдельное подключение по кнопке «Подключить Moodle» с хранением только refresh-токена в зашифрованном виде и возможностью отозвать в профиле. Почту — не подключаем.
  • Минимизация данных. Помощник хранит только то, что нужно для диалога (группа, роль); оценки, приказы, письма — показываются и не сохраняются. В логи — никогда.
  • Деградация. Портал недоступен → помощник говорит об этом и даёт прямую ссылку. Ничего не ломается: как с моделью в «упрощённом режиме».
  • Аудит. Каждое действие от имени пользователя — запись «кто, что, куда, когда» без содержимого. Для ИТ-службы это главный аргумент «мы контролируем».

Как это сформулировать менеджеру — три предложения

Было: бот, который отвечает на вопросы о технике и передаёт заявки специалисту.
Стало: единое окно студента — один чат в Telegram/VK/MAX/на сайте, который через единый вход ТПУ сам смотрит расписание, дедлайны и статусы заявок, создаёт справки и заявки в нужную систему и предупреждает о переносах пар и сроках.
Почему это реально: у ТПУ уже есть единая авторизация по OpenID Connect, центральный REST API личного кабинета, открытое API расписания и стандартные API у Moodle, облака и документации — нужно не строить, а подключаться, по одному порталу за раз, начиная с тех, что доступны без согласований.

Обход порталов выполнен 18.09.2026 с учётной записью студента; личные данные не копировались — только структура меню, каталоги услуг, адреса API и технические сигнатуры (заголовки, discovery-документы, статусы ответов).
