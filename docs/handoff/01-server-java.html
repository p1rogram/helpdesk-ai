Платформа, интеграции и эксплуатация

HTTP, вход, база данных, шина событий, боты, Naumen, деплой в закрытом контуре. Полный список файлов TypeScript-версии и во что они превращаются.

Роль одним абзацем

Ты делаешь всё, на чём стоит остальное: HTTP-сервер, вход пользователей, базу данных с миграциями, хранилище обращений, шину событий, интеграции с внешними системами (Kafka, боты, Naumen) и эксплуатацию в закрытом контуре вуза. Твой код — на Java, в отдельных Gradle-модулях platform, integrations, api-app, worker-app. Kotlin-модули (движок, ИИ) вызывают твои классы через интерфейсы; ты их не правишь, они — не твои.

Ты — единственный, кто ходит на сервер вуза. Остальные заканчивают работу зелёным CI и тегом версии; выкатка — твоя команда update.sh v1.x изнутри.

Критерий готовности

  • e2e/support-flow.spec.ts проходит против нового сервера без правок теста.
  • Все переменные из .env.example читаются с теми же именами и дефолтами.
  • Свежая БД поднимается миграциями; старая БД TypeScript-версии — тоже (Flyway baseline на schema_migrations).
  • Тела запросов и переписка не попадают в логи (см. serializers в app.ts:20).
  • update.sh: обновление одной командой, откат при неудачном /health.

Подводные камни

  • SSE через POST. Клиент шлёт сообщение POST-ом и читает поток в ответе (не EventSource). В Ktor — respondBytesWriter с text/event-stream, flush после каждого события, heartbeat : ping раз в 15 с.
  • Блокировка обращения. tryLock — атомарный UPDATE по busy_until; без него два параллельных сообщения ломают автомат.
  • Псевдонимизация. Имя пользователя никогда не хранится сырым — pseudonym(); в консоли оператора «Пользователь 1ED2CD».
  • Гостевые чаты удаляются по таймеру (purgeGuests) и не попадают в очередь/статистику — это фильтр NOT LIKE 'guest:%' в двух запросах.
  • Prod-запреты в конфиге: OPERATOR_OPEN_ACCESS=true в production — ошибка при старте.
