шаг 7JWT и вход /api/auth/dev1 день
Токен

HS256 на JWT_SECRET, claims (modules/auth/index.ts:98-114): sub (users.id), platform, puid, name, tenant, scope (guest|full), device (только гость), roles (список, может отсутствовать). Срок: JWT_TTL (12h), для гостя GUEST_JWT_TTL (1h).

Фильтр

OncePerRequestFilter: читает Authorization: Bearer …, проверяет подпись и срок, кладёт claims в SecurityContext. Три «уровня» (plugins/security.ts:78-125):

  • authenticate — любой валидный токен;
  • requireOperator — не гость и (OPERATOR_OPEN_ACCESS или platform:puid ∈ ADMIN_USERS или роль operator);
  • requireAdmin — только ADMIN_USERS.

                     разрешён только при WEB_DEMO_LOGIN=true (scope=full) / WEB_GUEST_LOGIN=true (scope=guest); иначе 403 {"error":"login_disabled"}

шаг 8Rate-limit, CORS, заголовки безопасностиполдня
  • Rate-limit: фильтр перед контроллерами. Ключ — u:<sub> из токена, иначе ip:<addr>; окно минута, лимит RATE_LIMIT_PER_MINUTE (90). Счётчик — WindowCounters.bump(key, 60000) в таблице rate_limits (общий для реплик). Отдельные лимиты на /api/auth/*: 10 в минуту. При превышении 429 + заголовки X-RateLimit-Limit / Remaining / Reset. /health и SSE-стрим очереди оператора — без лимита.
  • CORS: белый список CORS_ORIGINS; запрос без Origin — пропускать; чужой Origin — без CORS-заголовков (не 500). Методы GET/POST/PUT/DELETE, credentials=false.
  • Заголовки: X-Content-Type-Options: nosniff, Referrer-Policy, без CSP (CSP отдаёт Caddy для сайта).
  • server.forward-headers-strategy: framework — за Caddy настоящий IP в X-Forwarded-For.
  • Лимит тела запроса — BODY_LIMIT_BYTES (16 КБ).
Готово, когда: тест — 3 запроса при лимите 2 дают 200, 200, 429 (как db-infra.test.ts:70-95).

шаг 10SSE-поток сообщений — главный маршрут2 дня

POST /api/tickets/{id}/messages с телом {"text":"…"} (1–2000 символов). Ответ — не JSON, а поток text/event-stream, который клиент читает по мере прихода (routes/tickets.ts:85-127).

Последовательность
  1. Найти обращение по id и владельцу → 404.
  2. tryLock(id, 90 с) → если занято, 409 {"error":"busy"}. Это защита от двойного тапа: два прохода движка по одному состоянию ломают автомат.
  3. Ответить заголовками: Content-Type: text/event-stream; charset=utf-8, Cache-Control: no-cache, no-transform, X-Accel-Buffering: no, CORS-заголовок вручную (SSE идёт мимо CORS-фильтра — tickets.ts:170-180).
  4. Вызвать движок: engine.handle(ticket, user, text, scope, guestKey) — он отдаёт поток событий. Каждое событие писать как data: {json}\n\n и flush сразу. Раз в 15 с — : ping\n\n, чтобы прокси не закрыл соединение.
  5. Любое исключение → событие {"type":"error","message":"Не удалось обработать сообщение. Попробуйте ещё раз."}, стек в лог.
  6. finally: unlock, закрыть поток.
События (contract → ChatStreamEvent)
data: {"type":"meta","ticket":{…TicketCard}}
data: {"type":"status","text":"Определяю суть обращения…"}
data: {"type":"delta","text":"Похоже, это "}          ← много подряд, по мере генерации
data: {"type":"done","message":{…ChatMessage с quickReplies},"ticket":{…}}
data: {"type":"ack","ticket":{…}}                    ← принято, помощник молчит (обращение у оператора)
data: {"type":"error","message":"…"}
В Spring MVC

Вернуть ResponseBodyEmitter (или SseEmitter) и писать из отдельного потока; либо StreamingResponseBody с ручным write + flush. Движок — suspend-функция Kotlin, из Java вызывается через мост, который даст модуль engine (Flow → Iterator или callback). До появления движка — заглушка: на любой текст отдать meta → status → 3 delta → done с текстом «Эхо: …» и кнопками «Помогло / Не помогло». Этого хватает, чтобы отладить поток с фронтом.

Как проверить
curl -N -X POST localhost:8080/api/tickets/<id>/messages -H "Authorization: Bearer $T" -H 'content-type: application/json' -d '{"text":"не работает wifi"}'
# события должны появляться по одному, а не пачкой в конце — если пачкой, нет flush или буферизует прокси
Готово, когда: во фронте текст ответа «печатается» постепенно, статусы мелькают, кнопки появляются в конце; второй параллельный запрос получает 409; при исключении в движке фронт показывает ошибку, а не висит.

Подводные камни — прочитать до шага 10

  • SSE через POST, не EventSource. Клиент читает поток из ответа на POST (apps/web/src/lib/api.ts). Значит, обычный SseEmitter подходит, но заголовки и CORS ставишь сам. Проверь flush: если события приходят пачкой в конце — буферизует либо Spring, либо прокси (X-Accel-Buffering: no для nginx, flush_interval -1 уже есть в Caddyfile).
  • Один поток на запрос при стриме. Ответ модели длится 5–20 с. С Tomcat по умолчанию 200 потоков — на нагрузку вуза хватает; если станет тесно — spring.threads.virtual.enabled: true (Java 21) решает без переписывания.
  • JSONB-колонки. fields, tried_articles, pending_problems, pending_fields, meta — писать как ?::jsonb из строки Jackson, читать в Map<String,String> / List<String>.
  • Время — в UTC. Все TIMESTAMPTZ; в JSON — ISO-строки с Z. Дневные счётчики — по UTC-дате (today() в repository.ts).
  • Псевдонимизация. Имя пользователя нигде не хранится и не логируется. Единственный человекочитаемый идентификатор — «Пользователь 1ED2CD».
  • Гости не видны специалистам — фильтр в двух запросах (listForOperator, operatorStats); забудешь — гостевой мусор попадёт в статистику.
  • Не логировать тела. Ни запросов, ни ответов модели. Только id, метод, путь, статус, длительность.
  • Каталог — источник истины. Правки статей через admin API живут до следующего изменения JSON-файла; так задумано.
