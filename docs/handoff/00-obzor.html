Проект «Помоги мне» на Kotlin и Java

Что это, как устроено, кто что переписывает, какой стек и в каком порядке. Начинать отсюда; у каждой роли — свой документ с полным списком файлов.

Что это за проект и как он устроен

«Помоги мне» — помощник технической поддержки Томского политехнического университета. Студент пишет в чат (сайт, Telegram/VK/MAX Mini App или Android-приложение), помощник понимает проблему, задаёт уточнения, предлагает решение из базы знаний, а если не помогло — создаёт заявку специалисту или в help.tpu.ru. Специалист отвечает в консоли оператора, ответ уходит пользователю в чат и push в мессенджер.

Главный принцип, который нужно сохранить при переписывании: решения принимает код, а не модель. Языковая модель вызывается ровно в двух местах — «понять сообщение» (вернуть JSON по схеме) и «пересказать одну статью базы знаний». Кого звать, что спросить, когда создать заявку — решает детерминированный автомат (engine.ts), покрытый 91 тестом. Это и есть спецификация поведения: новая реализация готова, когда те же сценарии проходят.

Клиенты

Сайт и Mini App — один React-код с адаптерами платформ. Android — Compose. Все ходят в один HTTP API.

API

Один процесс: HTTP, auth, диалоговый движок, поиск, вызов модели. Стримит ответ по SSE.

Worker

Слушает Kafka: пуши в мессенджеры, аналитика. Боты Telegram/VK/MAX.

Данные

PostgreSQL 16 + pgvector. Каталог категорий и статей — JSON-файлы, импортируются при старте.

Модели

LLM — Qwen3-30B-A3B на DGX Spark вуза через vLLM (OpenAI-совместимый HTTP). Эмбеддинги — USER-bge-m3 там же. Облако Claude — запасной провайдер.

Эксплуатация

Docker Compose на сервере вуза без внешнего доступа. Обновление — вручную изнутри: update.sh <версия>.

Целевая структура репозитория

helpdesk/
├─ settings.gradle.kts, build.gradle.kts, gradle/libs.versions.toml
├─ shared/          KMP (commonMain: jvm + android)  ← Kotlin-shared
│   └─ src/commonMain/kotlin/…/{api,dialog,catalog,events}.kt, validation/, sse/
├─ platform/        Java: HTTP, auth, БД, миграции, конфиг       ← Серверный
├─ engine/          Kotlin: автомат диалога, шаблоны, каталог     ← Движок
├─ ai/              Kotlin: транспорт LLM, промпты, RAG, поиск     ← ИИ и поиск
├─ integrations/    Java: helpdesk (Naumen), боты, Kafka           ← Серверный
├─ api-app/         сборка API: platform + engine + ai → jar       ← Серверный
├─ worker-app/      сборка worker: integrations + Kafka-консьюмеры ← Серверный
├─ android/         Compose                                        ← Android
├─ web/             React/TS (текущий apps/web)                    ← Веб
├─ data/catalog/    JSON каталога (без изменений)
├─ deploy/, docker-compose.yml, .github/workflows/
└─ docs/

Правило зависимостей: platform и integrations не знают про engine и ai; engine зависит от ai только через интерфейсы (LlmService, SearchService); shared ни от кого не зависит. Так Java-модули и Kotlin-модули не лезут друг в друга.

Порядок работ

нед. 1
Скелет и контрактыGradle-проект с модулями; shared с data-классами контракта; интерфейсы выше как пустые Kotlin-интерфейсы; CI собирает и гоняет пустые тесты. Веб-фронт подключён к заглушке API.
нед. 2–3
Платформа + движок без моделиKtor: auth dev-входом, /api/tickets, SSE. Движок: автомат, уточнения, каталог, «упрощённый режим» без LLM. Цель: e2e-тест support-flow.spec.ts зелёный против нового сервера.
нед. 3–4
Модель и поискТранспорт к vLLM, промпты, разбор JSON, BM25, RAG с эмбеддингами через /v1/embeddings. Оценочный прогон на 30–50 реальных обращениях.
нед. 4–5
ИнтеграцииKafka, worker, бот Telegram (VK/MAX — вторыми), Naumen, консоль оператора. Корпоративный вход (SSO/LDAP/почта).
нед. 5–6
Эксплуатация и Androidupdate.sh с откатом, офлайн-комплект, бэкапы; Android на shared.

Словарь для тех, кто видит проект впервые

Обращение (ticket)
один диалог пользователя с помощником: состояние, категория, поля, история сообщений.
Состояния
intake → clarifying → solving → offer_escalation → escalated | closed; choosing_category при низкой уверенности.
Анализ (Analysis)
JSON, который возвращает модель на сообщение: категория, уверенность 0–1, суть, поля, тон, флаги «просит человека», «несколько проблем», «это вопрос».
Каталог
data/catalog/tpu.json: категории с уточняющими полями (clarify) и статьи с шагами решения. Импортируется в БД при старте, пересев по хэшу файла.
RAG
поиск по скачанной документации help.tpu.ru: фрагменты + векторы (pgvector) + BM25; результат отдаётся модели для ответа.
Эскалация
передача специалисту: operator (консоль) или helpdesk (заявка в help.tpu.ru/Naumen) — выбирается по категории.
Упрощённый режим
работа без модели: категория по ключевым словам, шаги статьи дословно. Включается при недоступной модели или исчерпанном бюджете гостя.
Гость
анонимный вход на сайте; видит только публичные темы; личность — cookie устройства; чаты не хранятся дольше часа.
Оператор / специалист
сотрудник поддержки в консоли: берёт обращение, отвечает, закрывает.
